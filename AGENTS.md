# Git workflow: no pull requests

This is a solo project. Ship finished branches by fast-forwarding straight into `master` and pushing — do not open a GitHub pull request and wait for it to be merged. It's fine to do work in a branch/worktree as usual; once a change is committed and verified, push it directly to `master` instead (e.g. `git push origin <branch>:master`, after confirming a clean fast-forward with `git merge-base --is-ancestor origin/master HEAD`). If `master` has diverged (not a fast-forward), stop and ask rather than force-pushing or merging around the conflict.

**After pushing: also sync the user's main checkout, not just the remote.** Work usually happens in an isolated worktree (`.claude/worktrees/*`), whose branch is separate from the `master` branch checked out in the user's actual dev checkout (`C:\Users\pavit\OneDrive\Desktop\OpenTracker`) — even though both share the same underlying `.git`, pushing to `origin/master` from a worktree does **not** advance that other checkout's local `master` ref. If you don't pull there too, the user's running Expo/Metro instance keeps serving stale code and any change looks like it "didn't happen," even though it's live on GitHub. So after a direct push to `master`, fast-forward the main checkout as well: `git -C "C:\Users\pavit\OneDrive\Desktop\OpenTracker" pull --ff-only` (check `git -C "<path>" status --short --branch` first — only pull if it's clean and simply behind; if it has diverged or has local changes, stop and ask instead of overwriting). This mirrors the `node_modules`-desync lesson in `PROJECT_STATUS.md`, section "Environment-Bug" — same root cause (worktree vs. main-checkout state drifting apart), different symptom.
