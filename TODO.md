## Konto-Löschung (Launch-Blocker #1, Teil A) — ✅ In-App-Teil abgeschlossen

Google Play verlangt für jede App mit Account-Erstellung einen in-App-Weg zur Konto-/Datenlöschung. Umgesetzt: neue Migration `supabase/migrations/0006_add_delete_account.sql` mit `delete_account()` (`security definer`, gleiches Muster wie `finish_workout`, prüft `auth.uid()` und bricht sonst mit `not authorized` ab). Alle nutzereigenen Tabellen kaskadieren bereits korrekt von `auth.users` (verifiziert gegen `0001`–`0005`); einzige Ausnahme ist `exercises.created_by` (`on delete set null` statt `cascade`), daher löscht die Funktion eigene Custom Exercises explizit vor dem `auth.users`-Delete. **Bewusste Entscheidung gegen `supabase.auth.admin.deleteUser()`**: dieser API-Weg braucht einen `service_role`-Key, der nie zum Client darf — hätte eine neue Edge Function erfordert (bisher keine im Projekt). Stattdessen der bestehende RPC-Weg (`supabase.rpc(...)`), konsistent mit jedem anderen Schreibzugriff im Code. **Härtung über das `finish_workout`-Vorbild hinaus**: `revoke execute ... from public/anon` zusätzlich zum `grant ... to authenticated` — die Supabase-eigenen Default-Privileges gewähren `anon`/`authenticated` sonst automatisch Ausführungsrechte auf jede neue `public`-Funktion, unabhängig von einem reinen `revoke ... from public` (verifiziert per `pg_proc.proacl` vor/nach dem zusätzlichen `revoke ... from anon`). Client-seitig: `deleteAccount()` in `src/features/auth/api/auth.api.ts` (RPC-Aufruf + `signOut()`), neuer „Konto löschen"-Button im Profil-Tab unter „Abmelden", gleiches zweistufiges `Alert.alert`-Bestätigungsmuster wie Routine-/Workout-Löschen. `database.types.ts` regeneriert.
